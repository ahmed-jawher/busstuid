# خطة بناء نظام "وصول آمن" (Wusool Safe) — سلامة الطلاب في النقل المدرسي
### الإصدار 4: نفس الإصدار 3 + تنفيذ ذاتي كامل بدون تدخل صاحب المشروع (بدون Docker على جهاز التطوير، قرارات محسومة مسبقاً، سير عمل Git آلي)

> هذا الملف موجّه إلى Claude Code. اقرأه كاملاً قبل كتابة أي كود، ونفّذ المراحل بالترتيب، ولا تنتقل لمرحلة قبل أن تنجح اختبارات المرحلة السابقة.
> **القسم 20 (التنفيذ الذاتي) له الأولوية على أي نص آخر في هذا الملف عند التعارض.**
> الأسماء التقنية (جداول، حقول، endpoints) بالإنجليزية، وواجهة المستخدم عربية أولاً (RTL) مع دعم الإنجليزية.

---

## 1. المشكلة والهدف

يُنسى أطفال داخل الباصات المدرسية وسيارات الأجرة الخاصة بعد انتهاء الرحلة، وقد يؤدي ذلك إلى الاختناق وضربات الحر، خصوصاً في صيف الخليج.

الهدف: نظام بسيط يسجّل فيه السائق صعود ونزول كل طالب **بضغطة على بطاقته (اسم + صورة)**، فيصل إشعار لحظي لولي الأمر. ولا يمكن إنهاء الرحلة بشكل طبيعي وفيها طالب مسجّل صعوده بلا نزول، وإذا حدث ذلك يُطلق إنذار. ويجب أن يعمل حتى لو **نسي السائق إنهاء الرحلة أصلاً**.

## 2. القيود الأساسية (من صاحب المشروع)

1. **لا QR ولا NFC ولا رموز في تشغيل الرحلة.** كل تسجيل صعود ونزول بالضغط داخل التطبيق. الرمز الوحيد في النظام هو رمز تأكيد البريد الإلكتروني عند التسجيل (القسم 5.1).
2. **لا تسجيل دخول عبر Google أو Apple أو أي طرف ثالث.** الحساب بالبريد الإلكتروني وكلمة مرور فقط، مع تأكيد البريد.
3. **لا SMS ولا مكالمات ولا أي خدمة مدفوعة بالرسالة.** الإشعارات عبر Web Push المجاني فقط (معيار VAPID، بدون Firebase).
4. **ولي الأمر لا يتفاعل** إلا لإنشاء حسابه وإضافة ملف طفله. الباقي إشعارات فقط، دون أي إجراء مطلوب منه.
5. أرخص بنية تشغيل ممكنة، مع قاعدة بيانات حقيقية (PostgreSQL، وليس SQLite في أي بيئة).
6. **بدون حسابات خارجية وبدون Docker أثناء التطوير:** كل شيء يعمل محلياً عبر حزم npm فقط: PostgreSQL 16 حقيقي عبر `embedded-postgres` (مجرَّب على جهاز صاحب المشروع ويعمل بدون صلاحيات مدير)، وملتقط بريد محلي. لا Firebase، ولا تخزين سحابي للصور. المفاتيح اللازمة يولّدها Claude Code بنفسه (القسم 9.2). Docker يُستخدم في **الإنتاج فقط**.

## 3. مبادئ التصميم (غير قابلة للتفاوض)

1. **السلامة قبل الراحة:** أي حالة غامضة تُعامل كخطر حتى يثبت العكس.
2. **لا شيء يُحذف في المسار الحرج:** أحداث الصعود/النزول والإنذارات append-only. التصحيح يتم بحدث جديد.
3. **الإنذار لا يُغلق إلا بإجراء بشري موثّق** (من السائق أو إدارة المنظمة، مع السبب).
4. **الحارس الزمني (Watchdog) مستقل عن السائق:** النظام يراقب الرحلات بنفسه ولا يعتمد على ضغطة "إنهاء الرحلة".
5. **الإنذار المحلي لا يحتاج إنترنت:** جهاز السائق يطلق صوت إنذار محلياً عند وجود طالب غير منزّل، حتى لو انقطعت الشبكة.
6. **Offline-first لتطبيق السائق:** الأحداث تُحفظ محلياً وتُرسل لاحقاً دون تكرار (idempotency).
7. **API-first:** الخادم مستقل تماماً عن الواجهة، والواجهة تتعامل معه عبر REST فقط.
8. **Wrap-ready من أول سطر:** الواجهة تطبيق ويب يعمل بالكامل في المتصفح (client-side)، ثم يُغلَّف بـ Capacitor لـ iOS وAndroid **بنفس الكود**. أي ميزة تعتمد على الجهاز تمر عبر طبقة `platform/` لها تنفيذ ويب وتنفيذ native (القسم 9.1).

## 4. الأطراف والأدوار

| الدور | الوصف | ماذا يفعل |
|---|---|---|
| `platform_admin` | مشغّل المنصة | إدارة عامة |
| `org_admin` | مدير جهة النقل: مدرسة، أو شركة نقل، أو سائق مستقل (السائق المستقل هو نفسه مدير منظمته) | يقبل الطلاب، يدير المركبات والسائقين، يتابع الإنذارات |
| `driver` | سائق باص أو أجرة خاص | يبدأ الرحلة، يضغط صعد/نزل/غائب، ينهي الرحلة |
| `attendant` | مشرفة الباص (اختياري) | نفس صلاحيات التسجيل |
| `guardian` | ولي الأمر | يضيف ملف الطالب **فقط**، ويستقبل الإشعارات، ويستطيع عرض السجل (قراءة فقط) |

## 5. رحلة ولي الأمر (أقل تفاعل ممكن)

1. ينشئ حساباً بالبريد الإلكتروني وكلمة مرور، ويُدخل رقم جواله (بدون تحقق)، ثم يؤكد بريده برمز يصله على الإيميل (القسم 5.1).
2. يسمح بالإشعارات (شاشة توضيحية واحدة لماذا هي ضرورية).
3. يضيف ملف الطالب: الاسم بالعربي والإنجليزي، صورة واضحة للوجه (إلزامية لأن السائق يتعرف عليه بها)، تاريخ الميلاد، المدرسة، **ورقم جوال السائق أو اختيار المدرسة من القائمة** لربط الطالب بجهة النقل، ثم موافقة الخصوصية (checkbox).
   - **حماية الربط برقم الجوال (لأن الأرقام غير موثّقة):** قبل الإرسال يُعرض لولي الأمر اسم السائق/المنظمة المطابق للرقم ليؤكده بضغطة. رقم الجوال فريد بين السائقين المستقلين (لا يُسمح لحسابين بنفس الرقم كسائق مستقل). ولا تظهر صورة الطالب ولا تاريخ ميلاده للمنظمة إلا **بعد** قبول الطلب؛ قبل القبول يرى المدير الاسم والمدرسة فقط.
4. انتهى دوره. طلب الربط يصل لمدير المنظمة (أو السائق المستقل) فيقبله ويعيّن الطالب لمسار/محطة.
5. بعدها يستقبل الإشعارات فقط، ويمكنه فتح التطبيق لرؤية حالة الطفل الحالية وسجل اليوم (قراءة فقط).

> ملاحظة: الغياب يسجّله السائق من التطبيق بضغطة، وليس ولي الأمر.

### 5.1 الحسابات والتحقق (لكل الأدوار)
- **التسجيل:** الاسم، البريد الإلكتروني، كلمة المرور، ورقم الجوال.
- **تأكيد البريد:** يصل رمز من 6 أرقام على الإيميل، صالح 10 دقائق، بحد أقصى 5 محاولات، مع زر "إعادة الإرسال" بعد 60 ثانية وحد أقصى 5 رسائل في الساعة لكل بريد. الرمز يُخزَّن hashed فقط. الحساب لا يستطيع إضافة طالب أو بدء رحلة قبل تأكيد البريد.
- **رقم الجوال بدون تحقق:** يُتحقق فقط من الصيغة (E.164، مع اختيار الدولة +973 أو +966 افتراضياً) باستخدام `libphonenumber-js`. يُعرض بعبارة "رقم غير موثّق" في لوحة المدير. استخدامه الوحيد: زر الاتصال `tel:` في شاشة الإنذار، وربط ولي الأمر بالسائق المستقل.
- **تسجيل الدخول لاحقاً:** بالبريد الإلكتروني أو رقم الجوال مع كلمة المرور (قرار المالك 2026-09-26، docs/DECISIONS.md؛ ورقم الجوال يُقبل فقط إذا كان لحساب واحد)، مع جلسة طويلة (refresh token لمدة 90 يوماً قابلة للإلغاء) حتى لا يُضطر السائق وولي الأمر لتسجيل الدخول كل مرة.
- **نسيت كلمة المرور:** رمز على البريد بنفس قواعد رمز التأكيد.
- **تغيير البريد:** يتطلب تأكيد البريد الجديد قبل اعتماده.
- **كلمات المرور:** argon2id، حد أدنى 6 أحرف أو أرقام بلا أي قيد آخر (قرار المالك 2026-09-26، docs/DECISIONS.md: ولي أمر لا يستطيع الدخول لحسابه لا يصله أي إنذار)، وقفل مؤقت 15 دقيقة بعد 10 محاولات فاشلة. فحص قائمة كلمات المرور الشائعة أُلغي.
- **المدراء:** نفس الطريقة، مع TOTP اختياري (تطبيق Authenticator، مجاني).
- **حذف الحساب:** زر داخل الإعدادات (شرط من Apple لأي تطبيق فيه إنشاء حساب).

**مزود البريد:** طبقة `EmailProvider` قابلة للاستبدال. في التطوير Mailpit محلياً، وفي الإنتاج مزود بطبقة مجانية أو منخفضة التكلفة (مثل Brevo أو Resend أو Amazon SES) مع إعداد SPF وDKIM وDMARC للنطاق حتى لا تذهب الرسائل للـ Spam. قالب البريد ثنائي اللغة بالهوية البصرية.

## 6. دورة حياة الرحلة (القلب الحرج للنظام)

```
scheduled → in_progress → completed
                       ↘ completed_with_alert (أُنهيت وفيها طالب غير منزّل)
أي رحلة نشطة → overdue (بواسطة Watchdog)
```

### 6.1 بدء الرحلة
- السائق يختار الرحلة من قائمة "رحلات اليوم" (تُولَّد تلقائياً من المسارات)، ويضغط "ابدأ".
- تظهر **قائمة الطلاب المتوقعين** كبطاقات كبيرة: صورة، اسم، المحطة.
- لا يمكن وجود أكثر من رحلة نشطة لنفس المركبة (قيد في قاعدة البيانات).

### 6.2 شاشة الرحلة (كل شيء بالضغط)
كل بطاقة طالب لها حالة ولون وأزرار حسب الحالة:

| الحالة | اللون | الأزرار المتاحة |
|---|---|---|
| `expected` (بانتظار الصعود) | رمادي | **صعد** / **غائب** |
| `boarded` (على المركبة) | أزرق | **نزل** |
| `alighted` (نزل) | أخضر | تراجع (خلال 60 ثانية فقط) |
| `absent` (غائب) | باهت | تراجع (خلال 60 ثانية فقط) |

- الضغط يسجّل الحدث فوراً محلياً مع: الوقت، الموقع GPS (لحظة الضغط فقط)، المستخدم.
- عدّاد ثابت أعلى الشاشة: "على المركبة: 7 · نزلوا: 12 · بانتظار: 3".
- ترتيب البطاقات: المنتظرون حسب ترتيب المحطات، ثم الذين على المركبة، ثم المنتهون في الأسفل.
- "التراجع" لا يحذف الحدث؛ يسجّل حدث تصحيح جديد.
- طالب غير موجود في القائمة: زر "إضافة طالب من المنظمة" يبحث بالاسم ويضيفه كـ `unexpected` مع إشعار للمدير.

### 6.3 إنهاء الرحلة
عند ضغط "إنهاء الرحلة":
1. إذا كان هناك طلاب بحالة `boarded`: **يُمنع الإنهاء الطبيعي**. تظهر شاشة حمراء بصورهم وأسمائهم، مع زر "نزل" بجانب كل واحد.
2. إذا بقي طلاب `expected` لم يُسجَّلوا: يطلب من السائق تحديد كل واحد إما "صعد" أو "غائب" قبل الإنهاء.
3. شاشة تأكيد أخيرة واحدة: "هل تأكدت أن المركبة خالية تماماً؟" بزر تأكيد (ضغطة واحدة، بدون مسح أي رمز).
4. زر "إنهاء رغم وجود طالب" متاح لكن بلون أحمر وتأكيد مزدوج، ونتيجته `completed_with_alert` وإنذار حرج فوري.

### 6.4 الحارس الزمني (Watchdog) — لأن السائق قد ينسى كل شيء
مهمة خلفية كل دقيقة تفحص الرحلات النشطة:
- تجاوزت الرحلة وقت الانتهاء المخطط + هامش (افتراضياً 15 دقيقة) → إنذار `trip_overdue` للسائق والمدير، ولأولياء أمور أي طالب ما زال `boarded`.
- آخر حدث أو نبضة من جهاز السائق أقدم من 10 دقائق وفي الرحلة طلاب على المركبة → إنذار للمدير.
- **على جهاز السائق نفسه:** إذا خرج السائق من التطبيق أو أُغلقت الشاشة والرحلة نشطة فيها طلاب، يُجدول إشعار محلي (Local Notification) يتكرر كل 5 دقائق "لديك طلاب على المركبة، أنهِ الرحلة". هذا يعمل بدون إنترنت.
- كل القيم قابلة للضبط لكل منظمة.

## 7. الإنذارات والتصعيد (Push فقط)

### أنواع الإنذارات
| النوع | الخطورة | المستلمون |
|---|---|---|
| `student_left_onboard` (أُنهيت الرحلة وطالب مسجّل على المركبة) | critical | السائق + ولي الأمر + مدير المنظمة |
| `trip_overdue` | high، ويصبح critical إن وُجد طالب على المركبة | السائق + المدير (+ ولي الأمر إن وُجد طفله على المركبة) |
| `driver_device_silent` | high | المدير |
| `unexpected_student` | low | المدير |

### التصعيد بدون أي تكلفة
بما أن الإشعار الوحيد هو Push، التعويض يكون بـ **التكرار والتوسيع**:
- **دقيقة 0:** Push عالي الأولوية للسائق وولي الأمر والمدير، مع صوت إنذار مخصص، وإنذار صوتي محلي مستمر على جهاز السائق حتى يتصرف.
- **كل دقيقتين:** إعادة إرسال Push حتى يُحلّ الإنذار.
- **دقيقة 5:** توسيع لكل مدراء المنظمة، ولولي الأمر الثاني إن وُجد، وتنبيه صوتي في لوحة الإدارة المفتوحة.
- **دقيقة 10:** إظهار رقم الطوارئ (999 في البحرين، 911 في السعودية حسب إعداد الدولة) بشكل بارز في كل الواجهات المعنية.

### إغلاق الإنذار
- يُغلق فقط من **السائق أو مدير المنظمة** (ولي الأمر لا يُطلب منه شيء).
- `resolved` يتطلب اختيار سبب من قائمة (وُجد الطالب في المركبة ونزل / نزل سابقاً ولم يُسجَّل / استلمه ولي الأمر...) وملاحظة اختيارية، ويُسجّل تلقائياً حدث نزول تصحيحي.
- عند الحل يصل ولي الأمر إشعار طمأنة: "تم التأكد من سلامة {student}".

### تنبيه صريح حول حدود Push (يُعرض في الإعدادات ولصاحب المشروع)
Push المجاني قد يتأخر أو لا يصل إذا كان الجوال مغلقاً أو في وضع توفير الطاقة. وفي مرحلة الويب، لا تصل الإشعارات على iPhone إلا إذا ثُبّت الموقع على الشاشة الرئيسية (iOS 16.4 فأحدث). هذا القيد يختفي بعد التغليف لأن التطبيق يستخدم الإشعارات الأصلية. لذلك:
- في نسخة الويب: شاشة إعداد إلزامية تشرح كيف يثبّت المستخدم التطبيق ويفعّل الإشعارات. وفي النسخة المغلّفة: طلب إذن الإشعارات الأصلي. وفي الحالتين **إشعار تجريبي** يؤكد أن الإشعارات تعمل.
- السائق لا يستطيع بدء رحلة إذا كانت الإشعارات معطّلة على جهازه.
- لوحة المدير تعرض أولياء الأمور الذين لم تصلهم آخر إشعارات (token منتهٍ أو إشعارات معطلة) ليتواصل معهم.
- خيار مستقبلي منخفض التكلفة: بوت Telegram مجاني كقناة ثانية، أو SMS مدفوع للإنذار الحرج فقط عند توفر ميزانية. صمّم طبقة القنوات كـ interface ليُضاف أي منهما لاحقاً بدون تعديل المنطق.

## 8. الإشعارات

- القناة: **Web Push بمعيار VAPID** عبر مكتبة `web-push` من الخادم مباشرة إلى المتصفح، بدون Firebase أو أي حساب. يعمل على Chrome وEdge وFirefox وSamsung Internet على Android، وعلى Safari في iPhone عند تثبيت التطبيق على الشاشة الرئيسية. إضافة لإشعارات داخل التطبيق (in-app inbox).
- طبقة `PushProvider` قابلة للاستبدال: `webpush` الآن، و`fcm` و`apns` تُضاف في مرحلة التغليف فقط.
- كل إشعار يُحفظ مع حالة الإرسال (`queued/sent/failed`) وسبب الفشل، وتُحذف الـ tokens المنتهية تلقائياً.
- قوالب ثنائية اللغة حسب لغة المستلم:
  - `boarded`: "✅ صعد {student} إلى {vehicle} الساعة {time}"
  - `alighted`: "🏫 نزل {student} عند {stop} الساعة {time}"
  - `absent`: "📋 سجّل السائق {student} غائباً عن رحلة {trip_name}"
  - `student_left_onboard`: "🚨 عاجل: {student} مسجّل على {vehicle} ولم يُسجَّل نزوله بعد انتهاء الرحلة. جوال السائق: {driver_phone}"
  - `resolved`: "✔️ تم التأكد من سلامة {student}"
- ولي الأمر يستطيع كتم إشعارات الصعود/النزول العادية من الإعدادات، **ولا يستطيع كتم الإنذارات الحرجة**.

| Web / App | **Vite + React + TypeScript** (SPA بالكامل على جهة العميل)، React Router، TanStack Query، Tailwind + shadcn/ui، vite-plugin-pwa | يُبنى إلى ملفات ثابتة (`dist/`) يمكن تغليفها مباشرة. لا Next.js ولا SSR لأن التطبيق المغلّف لا يملك خادماً |
| التغليف (لاحقاً) | **Capacitor** لـ iOS وAndroid | نفس كود الويب، مع إضافات أصلية للإشعارات والكاميرا والتخزين |
| Auth | بريد + كلمة مرور + تأكيد البريد برمز (القسم 5.1)، TOTP اختياري للمدراء، JWT في ترويسة `Authorization` (**لا cookies**)، و refresh token | بدون أي طرف ثالث، وBearer tokens تعمل في المتصفح وداخل WebView بنفس الطريقة |
| البريد | طبقة `EmailProvider`: Mailpit للتطوير، ومزود بطبقة مجانية للإنتاج | رموز التأكيد واستعادة كلمة المرور فقط |
| Push | Web Push (VAPID) عبر مكتبة `web-push` | مجاني وبدون أي حساب خارجي؛ المفاتيح تُولَّد محلياً |
| صور الطلاب | **داخل PostgreSQL** في جدول مستقل (`bytea`)، بعد ضغطها إلى WebP بحجم ≤ 100KB ومقاس 400×400 باستخدام `sharp` | بدون خدمة تخزين خارجية، وتدخل تلقائياً في النسخ الاحتياطي لقاعدة البيانات. 1000 طالب ≈ 100MB فقط |

| المراقبة | pino logs + Sentry (الطبقة المجانية) | Sentry **معطّل افتراضياً** ويعمل فقط إذا وُضع `SENTRY_DSN` في `.env`، حتى لا يُحتاج أي حساب |

### 9.1 الاستعداد للتغليف بـ Capacitor (يُطبَّق من المرحلة 0)

**طبقة `src/platform/`:** كل ما يخص الجهاز يُستدعى من واجهات (interfaces) موحّدة، ويُختار التنفيذ حسب `Capacitor.isNativePlatform()`. ممنوع استدعاء APIs المتصفح الخاصة بالجهاز مباشرة من المكوّنات.

| الواجهة | تنفيذ الويب (الآن) | تنفيذ native (بعد التغليف) |
|---|---|---|
| `push` | Web Push (VAPID) + Service Worker | `@capacitor/push-notifications` (FCM على Android، وAPNs على iOS مباشرة) — مرحلة التغليف فقط |
| `localNotifications` | Notification API (فقط والصفحة مفتوحة) | `@capacitor/local-notifications` (تعمل والتطبيق في الخلفية أو مغلق) |
| `offlineQueue` | IndexedDB | `@capacitor-community/sqlite` (لأن iOS قد يمسح تخزين WebView) |
| `secureStorage` (refresh token) | IndexedDB مع تشفير بسيط | Keychain/Keystore عبر إضافة secure storage |
| `geolocation` | Geolocation API | `@capacitor/geolocation` |
| `camera` (صورة الطالب) | `<input type="file" accept="image/*" capture>` | `@capacitor/camera` |
| `haptics` | `navigator.vibrate` إن توفّر | `@capacitor/haptics` |
| `keepAwake` | Wake Lock API | `@capacitor-community/keep-awake` |
| `appLifecycle` | `visibilitychange` | `@capacitor/app` (resume/pause، وزر الرجوع في Android) |

**قواعد تجعل التغليف سلساً:**
- عنوان الخادم من متغير بيئة `VITE_API_URL`، والتوجيه بـ Hash أو Browser Router مع إعداد يعمل تحت `capacitor://localhost`.
- CORS في الخادم يسمح بـ `capacitor://localhost` و`https://localhost` إضافة لنطاق الويب.
- تسجيل الدخول نموذج عادي داخل التطبيق (بريد + كلمة مرور) فيعمل كما هو داخل WebView بدون أي إضافة أصلية.
- التصميم يحترم `env(safe-area-inset-*)` للنوتش وشريط الحالة، ولا يعتمد على hover.
- كل الأصول (خطوط، أيقونات، أصوات الإنذار) مضمّنة محلياً في البناء، لا من CDN، لتعمل بدون إنترنت.
- الضغط على الإشعار يفتح الشاشة المعنية عبر deep link موحّد (`/trip/:id`, `/child/:id`, `/alert/:id`).
- جدول `push_subscriptions` يميّز المزود والمنصة، لأن الجهاز نفسه يحصل على اشتراك جديد بعد التغليف.

**أثر التغليف على الـ Watchdog:** كود JavaScript يتوقف عندما يذهب التطبيق للخلفية، فيتوقف النبض (heartbeat).
- عند `pause` يرسل التطبيق حدث `app_backgrounded` ويجدول **إشعارات محلية أصلية** تتكرر كل 5 دقائق طالما في الرحلة طلاب على المركبة.
- عند `resume` يلغيها ويستأنف النبض.
- الخادم لا يطلق `driver_device_silent` إذا كان آخر حدث `app_backgrounded`، ويعتمد بدلاً منه على `trip_overdue`.

### 9.2 التشغيل بدون أي تدخل يدوي (مرحلة التطوير)
- `pnpm setup` سكربت واحد يقوم بـ: نسخ `.env.example` إلى `.env`، توليد مفاتيح VAPID (`web-push generate-vapid-keys`)، توليد أسرار JWT وتشفير الحقول عشوائياً، تهيئة وتشغيل `embedded-postgres` على منفذ ثابت (54329) وحفظ بياناته في `.data/pg` (مُستثنى من Git)، تطبيق migrations، وتحميل بيانات seed.
- `pnpm dev` يشغّل قاعدة البيانات وملتقط البريد والخادم والواجهة معاً، ويكون النظام كاملاً جاهزاً للتجربة على `http://localhost`.
- رسائل البريد تظهر في صفحة ملتقط البريد المحلي (`http://localhost:8025`) بدون أي مزود بريد.
- إذا وُجد Docker على الجهاز لاحقاً، يبقى `docker-compose.prod.yml` صالحاً للتجربة، لكنه ليس مطلوباً للتطوير.
- Web Push يعمل على `localhost` بدون HTTPS لأنه يُعامل كـ secure context. للتجربة على جوال حقيقي في نفس الشبكة، أضف سكربت `pnpm dev:tunnel` اختياري.
- لا يُطلب من صاحب المشروع أي حساب أو مفتاح حتى نهاية المرحلة 5.

**ما يبقى بطبيعته يحتاج قراراً من صاحب المشروع (خارج نطاق الكود):**
- **الاستضافة عند الإطلاق:** أي خادم Linux عليه Docker يكفي. الكود يُسلَّم مع `docker-compose.prod.yml` جاهز (API + Web + Postgres + Caddy للـ HTTPS التلقائي)، فيكون النشر أمراً واحداً على أي VPS.
- **البريد في الإنتاج:** Mailpit للتطوير فقط؛ الإنتاج يحتاج مزود بريد ودومين حتى تصل الرسائل ولا تذهب للـ Spam. الطبقة جاهزة بإعداد SMTP عادي في `.env`.
- **متاجر التطبيقات والإشعارات الأصلية:** في المرحلة 6 فقط.

## 10. قاعدة البيانات (PostgreSQL)

### قواعد عامة
- المفاتيح `uuid` (v7)، الأوقات `timestamptz` بتوقيت UTC، والعرض بتوقيت المنظمة (`Asia/Bahrain` أو `Asia/Riyadh`).
- كل جدول تشغيلي فيه `organization_id` مع **Row Level Security**؛ الـ API يضبط `app.current_org_id` و`app.current_user_id` لكل transaction.
- soft delete للجداول المرجعية فقط؛ جداول الأحداث والإنذارات لا تُحذف ولا تُعدّل.

### الجداول

**الهوية والتنظيم**
- `organizations` (id, type: `school|transport_company|independent_driver`, name_ar, name_en, country: `BH|SA`, timezone, settings jsonb, status)
- `users` (id, email citext unique, email_verified_at nullable, phone_e164 not null, phone_verified boolean default false (دائماً false حالياً), full_name_ar, full_name_en, password_hash, failed_login_count, locked_until, totp_secret_encrypted nullable, preferred_locale, status, deleted_at)
- `email_codes` (id, user_id, purpose: `verify_email|reset_password|change_email`, target_email, code_hash, expires_at, attempts, consumed_at, created_at, request_ip)
- `memberships` (user_id, organization_id, role, status) — unique(user_id, organization_id, role)
- `push_subscriptions` (id, user_id, provider: `webpush|fcm|apns`, platform: `web|android|ios`, endpoint unique nullable, p256dh nullable, auth_secret nullable, native_token unique nullable, user_agent, last_test_ok_at, last_success_at, failed_count, revoked_at) — تُلغى تلقائياً عند رد 404/410 من خدمة Push
- `refresh_tokens` (user_id, token_hash, expires_at, revoked_at, device_info)

**الطلاب وأولياء الأمور**
- `students` (id, created_by_guardian_id, full_name_ar, full_name_en, date_of_birth, photo_version int, school_name, notes)
- `student_photos` (student_id PK, content bytea, mime_type, bytes, sha256, updated_at) — جدول مستقل حتى لا تُحمَّل الصور مع استعلامات الطلاب؛ تُقدَّم عبر `GET /students/:id/photo?v={photo_version}` بصلاحيات ومع `Cache-Control: private` و`ETag`
- `student_guardians` (student_id, guardian_user_id, relationship, is_primary)
- `enrollment_requests` (id, student_id, organization_id, requested_by, status: `pending|approved|rejected`, decided_by, decided_at) — ربط الطالب بجهة النقل؛ يُنشأ عند إضافة ولي الأمر رقم السائق أو اختيار المدرسة
- `org_students` (organization_id, student_id, status, joined_at) — يُنشأ عند الموافقة
- `consents` (guardian_user_id, student_id, purpose, policy_version, granted_at, withdrawn_at)

**المركبات والمسارات**
- `vehicles` (id, organization_id, plate_number, type: `bus|van|car`, capacity, status)
- `routes` (id, organization_id, name, direction: `to_school|to_home`, default_vehicle_id, default_driver_id, planned_start time, planned_end time, days_of_week int[])
- `route_stops` (id, route_id, sequence, name, location geography(Point) nullable)  — تتطلب إضافة PostGIS، أو استخدم (lat, lng numeric) إن أردت تجنب الامتداد
- `route_students` (route_id, student_id, stop_id, active_from, active_to)

**الرحلات والأحداث (المسار الحرج)**
- `trips` (id, organization_id, route_id nullable, vehicle_id, driver_id, direction, status, planned_end_at, started_at, ended_at, end_type: `normal|forced`, empty_confirmed_at, last_heartbeat_at)
  - `CREATE UNIQUE INDEX one_active_trip_per_vehicle ON trips(vehicle_id) WHERE status IN ('in_progress','overdue');`
- `trip_students` (trip_id, student_id, stop_id, status: `expected|boarded|alighted|absent|missing|resolved`, is_unexpected, boarded_at, alighted_at) — **projection** تُحدَّث في نفس transaction الحدث
- `trip_events` **append-only** (id, trip_id, student_id, event_type: `board|alight|absent|undo`, undoes_event_id nullable, recorded_by, client_event_id unique, client_recorded_at, server_received_at, lat, lng, accuracy_m)
  - `client_event_id` يمنع التكرار عند إعادة الإرسال من وضع offline.
  - trigger يمنع `UPDATE` و`DELETE`.
  - `undo` مسموح فقط خلال 60 ثانية من الحدث الأصلي (تحقق في الخادم بوقت الجهاز مع تسامح معقول).

**الإنذارات والإشعارات**
- `alerts` (id, organization_id, trip_id, student_id nullable, type, severity, status: `open|acknowledged|resolved`, escalation_level, opened_at, next_escalation_at, resolved_at, resolved_by, resolution_reason, resolution_note)
- `alert_events` append-only (alert_id, action: `opened|escalated|acknowledged|resolved|notified`, actor_user_id nullable, payload jsonb, created_at)
- `notifications` (id, user_id, alert_id nullable, template_key, payload jsonb, priority, created_at, read_at)
- `notification_deliveries` (notification_id, device_token_id, channel: `push`, status, attempts, last_error, updated_at) — `channel` enum قابل للتوسع مستقبلاً (`telegram`, `sms`)

**التدقيق**
- `audit_logs` append-only (actor_user_id, organization_id, action, entity_type, entity_id, ip, user_agent, diff jsonb, created_at) — يشمل عرض بيانات الطلاب وصورهم من لوحة الإدارة.

### آلات الحالة
عرّف آلات الحالة لـ `trip.status` و`trip_students.status` و`alert.status` في `packages/shared` كدوال نقية مع اختبارات، ويرفض الـ API أي انتقال غير مسموح برمز `409`.

## 11. واجهة الـ API (REST + OpenAPI)

الإصدار `/v1`، التوثيق عبر Swagger، وكل طلب كتابة في المسار الحرج يقبل ترويسة `Idempotency-Key`.

**المصادقة:** `POST /auth/register`, `POST /auth/verify-email`, `POST /auth/resend-code`, `POST /auth/login`, `POST /auth/forgot-password`, `POST /auth/reset-password`, `POST /auth/refresh`, `POST /auth/logout`, `DELETE /me` (حذف الحساب), `GET /push/vapid-public-key`, `POST /push/subscriptions` (تسجيل اشتراك الجهاز), `POST /push/subscriptions/:id/test` (إشعار تجريبي)

**ولي الأمر:** `POST /students` (مع رفع الصورة والموافقة وطلب الربط)، `GET /me/children`, `GET /children/:id/today`, `GET /children/:id/history`, `PATCH /me/notification-settings`

**المدير:** `GET /org/enrollment-requests`, `POST /org/enrollment-requests/:id/approve|reject`، إدارة المركبات والمسارات والسائقين وتعيين الطلاب (CRUD)، `GET /org/live`, `GET /org/unreachable-guardians`

**السائق:**
- `GET /driver/today`
- `POST /trips/:id/start`
- `GET /trips/:id/manifest` (مع روابط صور موقّعة ومؤقتة)
- `POST /trips/:id/events` — دفعة أحداث (board/alight/absent/undo) تدعم المزامنة بعد الانقطاع
- `POST /trips/:id/heartbeat` — كل دقيقتين أثناء الرحلة
- `POST /trips/:id/end` (مع `confirm_empty: true` أو `force: true` + سبب)

**الإنذارات:** `GET /alerts`, `POST /alerts/:id/acknowledge`, `POST /alerts/:id/resolve` (للسائق والمدير فقط)

## 13. الواجهات

### تطبيق السائق (ويب الآن، مغلّف لاحقاً) — الأهم
- شاشة الرحلة كما في القسم 6.2: شبكة بطاقات كبيرة بصور واضحة، زر واحد أو اثنان لكل بطاقة، أهداف لمس لا تقل عن 56px.
- اهتزاز خفيف وصوت قصير عند كل تسجيل ناجح، و toast فيه "تراجع" لمدة 60 ثانية.
- يعمل بدون إنترنت: طابور أحداث عبر `platform/offlineQueue`، مؤشر مزامنة واضح (✓ متزامن / ⏳ بانتظار الشبكة).
- الصور تُحمَّل مسبقاً وتُخزَّن محلياً عند بدء الرحلة لتعمل بدون شبكة.
- الوضع الداكن والخط الكبير افتراضياً للاستخدام داخل المركبة.
- إبقاء الشاشة تعمل أثناء الرحلة عبر `platform/keepAwake`.

### تطبيق ولي الأمر (قراءة فقط بعد الإضافة)
- شاشة إضافة طالب (نموذج واحد بخطوات قليلة، مع قص الصورة).
- بطاقة لكل طفل بحالته الآن: "على الباص منذ 6:42" / "وصل المدرسة 7:05" / "في انتظار رحلة العودة".
- سجل اليوم والأيام السابقة، صندوق الإشعارات، إعدادات الإشعارات.
- شاشة الإنذار الحرج بملء الشاشة مع زر اتصال بالسائق (رابط `tel:` مجاني) ورقم الطوارئ. لا يُطلب منه أي تأكيد.

### لوحة المدير (ويب)
- طلبات الربط الجديدة، إدارة المركبات والمسارات والسائقين وتعيين الطلاب للمحطات.
- الرحلات الحية بحالتها وعدّاداتها، شريط إنذارات ثابت مع صوت للحرجة.
- قائمة أولياء الأمور غير القابلين للوصول (إشعارات معطّلة).
- تقارير بسيطة وسجل تدقيق.

## 14. الخصوصية والامتثال (قانون حماية البيانات الشخصية البحريني رقم 30 لسنة 2018، ونظام حماية البيانات الشخصية السعودي)

- بيانات وصور أطفال: موافقة صريحة موثّقة من ولي الأمر عند إضافة الملف، مع نص إشعار الخصوصية ورقم إصداره.
- الصور لا تُعرض إلا للسائق والمدير في المنظمة المرتبطة، بروابط موقّعة تنتهي خلال دقائق، وتُحذف من ذاكرة جهاز السائق عند انتهاء اليوم.
- الموقع الجغرافي يُسجَّل **فقط لحظة ضغط السائق** على حدث، بدون تتبع مستمر.
- تقليل البيانات: لا أرقام هوية، لا عنوان منزل نصي.
- التشفير: TLS في النقل، تشفير القرص، ونسخ احتياطية مشفّرة.
- الاحتفاظ الافتراضي (قابل للضبط): أحداث الرحلات سنة دراسية + سنة، الإنذارات وسجل التدقيق 3 سنوات، وحذف الصورة فور إلغاء ربط الطالب أو سحب الموافقة.
- حقوق صاحب البيانات: ولي الأمر يطلب تصدير أو حذف بيانات طفله من الإعدادات (استثناء: سجلات الإنذارات لأغراض قانونية).
- هذا القسم تصميم تقني وليس استشارة قانونية؛ يُراجع قبل الإطلاق.

## 15. الهوية البصرية (الخطوط والثيم)

الواجهة يجب أن تبدو كمنصة حكومية رسمية موثوقة. كل القيم **Design Tokens** في `packages/ui-tokens` لتنتقل كما هي للتطبيق، مع ثيمين يُختاران من إعداد الدولة للمنظمة:

- **ممنوع** استخدام أي شعار أو اسم أو ختم لجهة حكومية، أو أي عبارة توحي بأن النظام صادر عن حكومة. "المظهر الرسمي" يعني الألوان والخطوط والتباعد فقط.
- **الخط:** `IBM Plex Sans Arabic` (مجاني، ومعتمد في دليل "كود المنصات" لهيئة الحكومة الرقمية السعودية)، أوزان 400/500/600/700، مع بديل `Tahoma, system-ui, sans-serif`.
- **ثيم `sa`:** مستوحى من كود المنصات السعودي، اللون الأساسي أخضر حكومي.
- **ثيم `bh`:** مستوحى من الهوية الرسمية البحرينية، اللون الأساسي أحمر علم البحرين مع الأبيض.
- ⚠️ القيم اللونية الدقيقة تُطابق مع الأدلة الرسمية المنشورة قبل الإطلاق؛ ضع قيماً مؤقتة مع تعليق `// TODO: verify against official guideline`.
- ألوان الحالات ثابتة ولا تعتمد على اللون وحده (أيقونة + نص): رمادي بانتظار، أزرق على المركبة، أخضر نزل، أحمر داكن للإنذار (مختلف عن أحمر الهوية البحرينية).
- RTL افتراضياً باستخدام logical properties، وأرقام لاتينية مع خيار عربية، ووضع داكن، وتباين WCAG AA على الأقل.

## 16. الاختبارات (إلزامية للمسار الحرج)

- **وحدات:** آلات الحالة، قواعد الإنهاء، نافذة التراجع، جدول التصعيد.
- **تكامل (PostgreSQL 16 حقيقي عبر `embedded-postgres`، بقاعدة مستقلة لكل ملف اختبار عبر `CREATE DATABASE ... TEMPLATE`)، ومُرسل Push وهمي يسجّل الرسائل (إضافة لاختبار واحد حقيقي لـ Web Push عبر Playwright بمتصفح Chromium):**
  1. طالب صعد ولم ينزل → الإنهاء الطبيعي مرفوض.
  2. إنهاء قسري مع طالب على المركبة → إنذار critical + Push للسائق وولي الأمر والمدير.
  3. السائق لم ينهِ الرحلة إطلاقاً → Watchdog يطلق `trip_overdue` بعد الهامش.
  4. توقف نبض جهاز السائق مع طلاب على المركبة → `driver_device_silent`.
  5. أحداث مكررة بنفس `client_event_id` → تُسجّل مرة واحدة.
  6. أحداث offline تصل متأخرة وبغير ترتيب → الحالة النهائية صحيحة حسب `client_recorded_at`.
  7. إعادة تشغيل الخادم أثناء إنذار مفتوح → التصعيد يستمر.
  8. التصعيد يتكرر حتى الحل ويتوقف فوراً بعده.
  9. ولي الأمر لا يستطيع حل إنذار ولا رؤية إلا أطفاله.
  10. مستخدم من منظمة A لا يرى بيانات منظمة B (RLS).
  11. سائق بإشعارات معطّلة لا يستطيع بدء رحلة.
  12. حساب بريده غير مؤكد لا يستطيع إضافة طالب ولا بدء رحلة، ورمز منتهٍ أو بعد 5 محاولات يُرفض، وحد إعادة الإرسال يعمل.
- **E2E (Playwright):** إضافة طالب وقبوله، رحلة صباح كاملة، رحلة عودة، وسيناريو الطفل المنسي.
- تغطية لا تقل عن 90% لوحدات `trips` و`alerts` و`notifications`.

## 17. مراحل التنفيذ

**المرحلة 0 — التأسيس:** المستودع، `tools/dev-stack` (embedded-postgres + ملتقط البريد)، سكربت `pnpm setup` يولّد كل المفاتيح والأسرار تلقائياً (القسم 9.2)، lint، CI، `packages/ui-tokens`، هيكل `src/platform/` بواجهاته وتنفيذات الويب، وملف `CLAUDE.md` يلخّص الأقسام 2 و3 و9.1.
✅ القبول: `pnpm dev` يشغّل كل شيء و`pnpm test` يعمل.

**المرحلة 1 — البيانات والهوية:** المخطط مع migrations، RLS، triggers الـ append-only، التسجيل وتأكيد البريد وتسجيل الدخول واستعادة كلمة المرور (القسم 5.1) مع Mailpit، رفع الصور وضغطها وتخزينها في PostgreSQL، تسجيل اشتراكات Web Push، بيانات seed واقعية (مدرسة، سائق مستقل، 3 مركبات، 40 طالباً بصور placeholder، أولياء أمور).
✅ القبول: اختبارات RLS والأدوار والحسابات (9، 10، 12) ناجحة.

**المرحلة 2 — الرحلة:** توليد الرحلات، البدء، أحداث الصعود/النزول/الغياب/التراجع، المزامنة الدفعية، النبض، الإنهاء بقواعده.
✅ القبول: الاختبارات 1، 5، 6 ناجحة.

**المرحلة 3 — الإشعارات والإنذارات:** Web Push (VAPID) وService Worker، القوالب، التصعيد، Watchdog، الإشعار المحلي على جهاز السائق، reconciliation.
✅ القبول: الاختبارات 2، 3، 4، 7، 8، 11 ناجحة.

**المرحلة 4 — الواجهات:** واجهة السائق وولي الأمر ولوحة المدير في تطبيق Vite واحد بمسارات حسب الدور، بالهوية البصرية، مع شاشات تفعيل الإشعارات، واختبارها على شاشات الجوال (375px) كأولوية.
✅ القبول: سيناريوهات E2E الأربعة.

**المرحلة 5 — التحصين:** rate limiting، سجل التدقيق الكامل، الاحتفاظ والحذف، سكربت النسخ الاحتياطي، دعم Sentry الاختياري، `docker-compose.prod.yml` مع Caddy، اختبار حمل آلي (200 رحلة متزامنة بسكربت k6 أو autocannon)، و**محاكاة ميدانية آلية** (سكربت يحاكي سائقاً ومدرسة يوماً كاملاً مع انقطاع شبكة وإغلاق تطبيق) بدلاً من التجربة الميدانية البشرية، التي تُترك لصاحب المشروع بعد التسليم.

**المرحلة 6 — التغليف لـ iOS وAndroid (Capacitor):**
> **في التنفيذ الذاتي (القسم 20) تُنفَّذ المرحلة 6 جزئياً فقط:** إضافة Capacitor وإنشاء مشروعي `android/` و`ios/`، كتابة كل التنفيذات الأصلية في `src/platform/native/`، ومزودي `fcm` و`apns` في الخادم مع اختبارات بمُرسل وهمي، وسكربت بناء APK تجريبي لـ Android إن أمكن تثبيت JDK وAndroid SDK محلياً بدون صلاحيات مدير. **لا يُنفَّذ:** بناء iOS (يتطلب جهاز Mac)، ومفاتيح Firebase/APNs، والنشر في المتاجر؛ تُوثَّق خطواتها في `docs/RELEASE.md` لصاحب المشروع.
- `npx cap add ios` و`npx cap add android`، ثم كتابة التنفيذات الأصلية لكل واجهة في `src/platform/native/`.
- **هذه المرحلة الوحيدة التي تحتاج حسابات خارجية**، لأن الإشعارات الأصلية على Android تمر إلزامياً عبر Firebase Cloud Messaging، وعلى iPhone عبر خدمة Apple (APNs). لا يوجد بديل عملي لهما في التطبيقات الأصلية. يحتاج صاحب المشروع لتوفير: ملف `google-services.json` وملف service account من Firebase، ومفتاح APNs (`.p8`) من حساب Apple Developer. Claude Code يكتب مزودي `fcm` و`apns` في طبقة `PushProvider` ويرسل لهما من الخادم مباشرة.
- قناة إشعارات Android بأولوية قصوى وصوت إنذار مخصص للإنذارات الحرجة، وعلى iOS صوت مخصص، مع طلب صلاحية Critical Alerts من Apple لاحقاً (تحتاج موافقة خاصة).
- لا حاجة لـ Sign in with Apple لأن النظام لا يستخدم أي تسجيل دخول من طرف ثالث.
- الأيقونات وشاشة البداية (`@capacitor/assets`)، ودعم زر الرجوع في Android.
- اسم تطبيق واحد في المتاجر يحتوي واجهة السائق وولي الأمر حسب الدور؛ لوحة المدير تبقى ويب.
- تجربة على أجهزة حقيقية: الإشعار والتطبيق مغلق، وضع توفير الطاقة، انقطاع الشبكة أثناء الرحلة.
✅ القبول: كل اختبارات E2E تنجح على الويب، ووصول الإشعار الحرج والتطبيق مغلق على جهازي iPhone وAndroid حقيقيين.

> ملاحظة للمتاجر: Apple قد ترفض تطبيقاً يبدو مجرد موقع مغلّف (Guideline 4.2). استخدام الإشعارات الأصلية والإشعارات المحلية والكاميرا والاهتزاز يجعله تطبيقاً فعلياً. التكلفة: حساب Apple Developer سنوي، وحساب Google Play برسوم لمرة واحدة.

## 19. تعليمات عامة لـ Claude Code
- اسأل قبل تغيير أي قرار في الأقسام 2 و3 و6 و7 و9.1.
- لا تستخدم أي ميزة تحتاج خادم واجهة (SSR، API routes داخل الواجهة، server actions)؛ الواجهة ملفات ثابتة فقط.
- لا تستدعي APIs الجهاز مباشرة من المكوّنات؛ دائماً عبر `src/platform/`.
- لا QR ولا NFC ولا SMS، ولا تسجيل دخول عبر Google/Apple. الرمز الوحيد المسموح هو رمز البريد في القسم 5.1.
- لا تستخدم SQLite على الخادم في أي بيئة، بما فيها الاختبارات.
- كل migration قابلة للتراجع، ولا تعدّل migration منشورة.
- كل نص واجهة في ملفات ترجمة (`ar.json`, `en.json`).
- اكتب ملخصاً في `docs/CHANGELOG.md` بعد كل مرحلة.

## 20. التنفيذ الذاتي (بدون تدخل صاحب المشروع)

صاحب المشروع فوّض Claude Code بالتنفيذ الكامل. القاعدة: **لا تتوقف لتسأل؛ اختر الخيار الأكثر أماناً للأطفال ثم الأبسط، ووثّق القرار.**

### 20.1 المستودع وGit
- المستودع: `https://github.com/ahmed-jawher/busstuid` (المالك `ahmed-jawher`؛ لصاحب المشروع صلاحية push). يُستنسخ في `D:\Downloads\busstuid`.
- اسم المستودع يبقى `busstuid`؛ اسم المنتج والحزم داخل الكود `wusool-safe` (`@wusool/api`, `@wusool/web`, ...).
- لكل مرحلة فرع `phase-N-<name>`، مع commits صغيرة ومتكررة، ثم Pull Request إلى `main`. **يُدمج الـ PR تلقائياً (squash)** فقط بعد نجاح كل اختبارات المرحلة وlint وtypecheck، ثم يُحذف الفرع ويبدأ فرع المرحلة التالية من `main` المحدّث.
- CI عبر GitHub Actions (مجاني للمستودعات العامة)، وتُستخدم `embedded-postgres` داخل CI أيضاً.
- **ممنوع:** force push على `main`، حذف المستودع، تغيير إعدادات المستودع أو صلاحياته، رفع أي سر (`.env` و`.data/` في `.gitignore`، مع فحص آلي قبل كل commit يرفض أي نص يشبه مفتاحاً خاصاً أو token).

### 20.2 أدوات يثبّتها Claude Code بنفسه (بدون صلاحيات مدير)
- `pnpm` عبر `npm i -g pnpm` (في مجلد المستخدم).
- PostgreSQL 16 عبر `embedded-postgres`، وملتقط البريد، وChromium لـ Playwright — كلها حزم npm داخل المشروع.
- في المرحلة 6 فقط: JDK وAndroid command-line tools كملفات مضغوطة في مجلد المستخدم إن احتيج لبناء APK. إن فشل ذلك، يُوثَّق ويُتجاوز دون إيقاف العمل.

### 20.3 قرارات محسومة مسبقاً
| المسألة | القرار |
|---|---|
| ربط الطالب برقم جوال غير موثّق | القسم 5 (تأكيد الاسم، رقم فريد للسائق المستقل، الصورة بعد القبول فقط) |
| صور الطلاب في `<img>` | روابط موقّعة HMAC تنتهي خلال 5 دقائق (لأن `<img>` لا يرسل ترويسة Authorization) |

| توليد uuid v7 | في طبقة التطبيق (PostgreSQL 16 لا يدعمه أصلياً) |
| RLS مع Prisma | الخادم يتصل بدور قاعدة بيانات غير مالك للجداول (`wusool_app`) مع `FORCE ROW LEVEL SECURITY`، وكل طلب داخل transaction تضبط `set_config('app.current_org_id', ..., true)` |
